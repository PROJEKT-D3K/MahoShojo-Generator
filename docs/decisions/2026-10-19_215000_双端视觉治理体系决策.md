# ADR：双端视觉治理体系

- 日期：2026-10-19
- 状态：`accepted`（治理框架已接受；各层实现按批次落地，落地状态以代码与测试为准）
- 决策标识：`ADR-visual-governance-v1`
- 规范：[双端视觉基线与工程契约规格](../specs/2026-10-19_215200_双端视觉基线与工程契约规格.md)（`SPEC-visual-baseline-v1`）
- 上位约束：[Desktop 产品架构与 Web 共源决策](./2026-10-02_184000_Desktop产品架构与Web共源决策.md)（DESK-PROD-009：主题单点维护、不以逐像素为门禁）

规范性词汇沿 RFC 2119 / RFC 8174。

## 1. 背景

DESK-PROD-009 已冻结「主题、品牌资源和共享控件 **MUST** 单点维护」「视觉差异有原因，不以逐像素相同为门禁」。当前已就位的基础设施：设计 token 单源（`packages/ui-web/src/styles.css` 的 `--app-*`/`--creator-*` 三段主题解析）、共享组件双端共消费（`@mahoshojo/ui-web`）、产物级构建门禁（`tests/shared-theme-build-output.test.ts`、`tests/shared-markdown-css.test.ts`）、ui-web host-neutral 边界检查。

截至本决策日仍存在的系统性缺口：

- 无成文的 token 分层/命名规范与组件写法政策；token 只有颜色与字体栈，间距/圆角/字号/阴影/z-index 无刻度化定义；
- 无机器可执行的设计契约门禁——现有测试验证「共享 CSS 进入了产物」，不验证「`var()` 可解析、对比度达标、token 不被宿主重定义、硬编码字面量不增长」；
- 无组件集中审查入口——共享组件只能靠单测与真实页面肉眼发现，审查双端一致性需要逐页对照；
- 宿主私有残留（Web `.arena-cta-button`/`.admin-button-sm`/`blue-theme.css`、Desktop 未被消费的 `@theme --color-*` 调试主题）与双份字面量（结果卡渐变等）存在；
- 写法机制异质无约束：Web 端并存 Tailwind utility、共享 CSS 类、CSS Module、styled-jsx、inline style。

## 2. 决定

### 2.1 采纳五层视觉治理体系

1. **规范层**：`docs/specs/` 成文视觉基线与工程契约（`SPEC-visual-baseline-v1`），规定 token 所有权、写法政策、门禁义务、样板间义务与验收口径；
2. **token 层**：`--app-*`/`--creator-*` 单一权威于 `packages/ui-web/src/styles.css`，按批次补间距/圆角/字号/阴影/z-index 刻度；
3. **契约门禁层**：纯 node 秒级单测进 `workspace:checks`，验证规则未被破坏；
4. **样板间层**：`packages/ui-web` 单源 `ShowroomView`，挂 Web 与 Desktop 各自的 dev 路由双消费同一组件；
5. **巡检层**：显式本地命令 + Playwright 条件矩阵 + 证据留痕（report.json/截图），不进 CI。

### 2.2 门禁哲学

机器硬门禁只验证「规则未被破坏」（`var()` 可解析、token 所有权、对比度阈值、字面量基线不增长），不判断「长得对不对」。外观验收保持本地显式命令 + 人工看图 + 证据元数据记录。**不引入像素 diff、黄金图基线或 CI 截图门禁**——这既延续 DESK-PROD-009 已接受口径，也是本决策新增的明确边界。

### 2.3 共源样板间优先于 Storybook

本期不引入 Storybook，先建应用内共源样板间：本仓共享组件是业务级组件、依赖宿主 provider（color-mode、router、stores、domain contracts），Storybook 需要成规模的 mock/decorator 才能隔离；而挂 dev 路由的样板间运行在真实应用壳内，零 mock，且在 Desktop 侧直接获得真实 WebView2 验收能力——正好补上历次验收中反复出现的「真实 WebView2 待验」缺口。出现 `SPEC-visual-baseline-v1` 所列再评估触发条件时，Storybook 另行专项评估，届时应以独立构建器直接消费 ui-web 源文件，不继承任一 app 框架链。

### 2.4 组件原语按需渐进抽取

只在修复具体不一致或新增共享控件时抽取原语级组件（如 Button/Field/Panel）进入 ui-web 并同步样板间；不对存量做大迁移。原语层的成形靠累积而非一次重构。

### 2.5 范围限定

本体系适用于 `apps/web`、`apps/desktop`、`packages/ui-web`。`apps/admin` 是独立管理端（独立 esbuild 客户端与手写样式体系、不依赖 ui-web），不纳入本体系约束，仅在此登记说明；未来若管理端与产品面出现共享需求，另行决策。

## 3. 影响

- `workspace:checks` 新增设计契约测试族；存量违规以 baseline/豁免清单登记，门禁对增量从严——首次落地可能暴露已存在的对比度不达标项，按 spec 流程登记为已知缺口单独修复，不在门禁落地批次中混改颜色。
- 新增/显著变更共享组件产生新义务：同一工作单元更新样板间分区；写法政策约束此后新代码。
- 文档：`docs/decisions/README.md` 与 `docs/README.md` 索引同步；流程固化后续沉淀 `.agents/skills/` repo skill。
- 无新增生产依赖；契约测试只用已锁定的 vitest/postcss 依赖。

## 4. 不采用的方案

- **本期直接引入 Storybook**：依赖树与 mock 成本高，且无法覆盖真实 WebView2；保留显式触发条件而非永久拒绝（§2.3）。
- **像素 diff / 黄金图 / CI 截图门禁**：与已接受口径冲突，误报率高且把「看图」责任转嫁给脆弱的基线维护。
- **全套 stylelint**：核心规则由契约测试直接表达更贴合本仓结构；若未来证明需要再评估。
- **把 color-mode 三段解析改写为 Tailwind `@theme`**：`styles.css` 头注已记录 `@theme` 单点 `:root` 输出无法表达「系统偏好 vs 显式选择」的优先级语义。
- **admin 纳入统一视觉体系**：其独立样式体系与产品面无共享需求，纳入只会制造无收益的重写。
- **组件原语一次性大重构**：超出当前收益，按需抽取更可控。
