# Desktop 多人房间 Windows 有限验收

本流程使用两个一次性 Desktop 副本、两个合成账号和本机 HTTPS/WSS 服务，验证真实 Native、WebView2、系统凭据存储与房间会话页面。覆盖大厅、创建、加入、读取、presence、退出、关闭、房主配置发布、成员提案、房主审阅及结果未知核对；当前房间战报另用固定合成 fixture 验证读取、实时预览与恢复。不调用模型或生产服务，不验真实协作生成。

## 准备

使用包含本 harness 的干净源码 checkout，预先具备仓库指定的 Node、pnpm、Rust/MSVC、WebView2、依赖和 Cargo 离线缓存。脚本不安装工具或 WebView2，不启动安装包。构建需要两个独立 Cargo target 的磁盘空间；空间不足时停止，不清理原资料或证据。

在 PowerShell 中设置三个互不包含的绝对路径；两个副本还必须与源码目录分离，状态目录必须尚不存在。禁止 symlink/junction、额外 `.env` 或平台 Tauri 覆盖配置。

```powershell
$Source = (Get-Location).Path
$HostCopy = '<隔离目录>\host-copy'
$MemberCopy = '<隔离目录>\member-copy'
$State = '<隔离目录>\run-state'
git clone --no-hardlinks $Source $HostCopy
git clone --no-hardlinks $Source $MemberCopy
```

在两份副本各自准备既有离线依赖，保持 Git 干净；没有缓存就先补齐正常开发环境，不能通过本 harness 自动下载或改安全设置。

```powershell
pnpm --dir $HostCopy install --frozen-lockfile --offline
pnpm --dir $MemberCopy install --frozen-lockfile --offline
node scripts/desktop-room-acceptance.mjs preflight --host-tree $HostCopy --member-tree $MemberCopy --state-root $State
node scripts/desktop-room-acceptance.mjs prepare --host-tree $HostCopy --member-tree $MemberCopy --state-root $State
node scripts/desktop-room-acceptance.mjs self-check --state-root $State
node scripts/desktop-room-acceptance.mjs build --state-root $State
node scripts/desktop-room-acceptance.mjs launch --state-root $State
```

两份 `--debug --no-bundle` 构建串行完成后才启动两个独立可执行文件，不运行 Vite，不竞争开发服务器端口。只允许固定 Room `room.acceptance.invalid:34443` 映射到 `127.0.0.1`，以及合成登录 `http://127.0.0.1:34080`。两监听器实际绑定且自检成功后才启动 App；端口已占用会退出，不连接占用者。

每个副本有独立 identifier、SecretStore service、AppData、WebView 数据目录、单实例锁和 target。保留原受保护 account-session 槽名，由不同 service 隔离。副本必须由 launcher 启动；release 编译拒绝。两个页面通过原 Native 浏览器登录流程分别选择合成账号 101 和 202，保留 PKCE、state、一次性 exchange 和真实 OS keyring。不要输入真实账号、API Key 或其他用户凭据。

## 操作与观察

1. 保持隔离副本的初始空白测试草稿，101 在 `/arena` 打开多人大厅并创建；只有出现来源不完整提示时，才会显示“明确创建空草稿房间”按钮。202 刷新大厅后加入。只有收到真实 snapshot 和包含自身的 presence 才应显示在线
2. 验证房主和成员列表、普通 Arena 草稿/模型偏好仍保留，成员可编辑独立提案草稿，房主可审阅；协作生成仍没有可执行按钮
3. 在同一成员窗口明确断开本机房间连接，房主应看到离线且成员席位仍保留；成员随后重新打开大厅并明确加入原房间。这只验证离线和显式重新加入；单独切断 WSS 的恢复按下方战报增量另验。单独关闭窗口只验退役；本次运行不重新启动已关闭的副本
4. 202 离开只撤销自己的成员资格；101 关闭使房间终结。确认弹框不得跨切号、重新登录或房间变化复用
5. launcher 控制台输入 `fault create` 后，由 101 新建房间。服务在真实 receipt/checkpoint 已提交后丢响应；页面应显示结果未知。显式恢复原创建意图须使用原 ID/body 的 resume-only，不能另建房间
6. 分别用 `fault join`、`fault leave`、`fault close` 制造相同丢回执。通过读取原房间核对；不得自动重发原 mutation
7. 同账号重新登录、切账号、返回或重新加载后，旧账号/Document 的结果不得更新新页面。记录是否有错误复活、重复创建、永久等待或错误在线状态

### 房主配置发布增量

- 当前 Desktop 连接房间时仍冻结本机草稿编辑。需要制造配置差异时，房主先明确断开本机连接（不关闭房间），修改一个可共享设置，再同账号加入原房间；服务保留既有房主身份。随后点击“比较本地与房间设置”，核对差异后再两次明确发布；取消确认不写入，连续点击不重复派发。成员没有配置发布入口。成功后房主和成员应观察到同一新修订，本地正文/草稿和模型偏好不被替换。
- 先按上一步准备与房间不同的本地配置，控制台 `fault config` 后再由房主显式发布：服务先提交配置再丢响应。页面须保留未知，不能自动重发；“核对当前房间”即使读到目标相同，也只说明当前状态，不能宣布原请求成功。“结束本次跟踪”需独立确认，文案须说明不取消服务器请求；随后必须“重新读取房间”，再重新比较并显式发布。普通断开/窗口退役不能代替明确结束；同进程 Document reload/重新挂载恢复时原目标不可恢复，不以当前草稿重建它。
- 控制台 `fault config-unsupported` 模拟旧 adapter 在业务前拒绝下一次配置发布：页面应明确提示“服务器不支持此桌面操作，请更新服务端后再明确重试”，`observe` 中对应 `config` 为 400、未丢响应；房间修订/配置不变，不尝试 legacy 请求。此开关只复现旧协议拒绝语义，不声称启动了旧版本完整服务。它不被 GET 或无效 owner header 消费，且仅生效一次；后续新比较、新确认可正常发布。
- 比较/发布确认或未知核对过程中，测试同账号重新登录、切账号、房间变化；旧确认不得更新新身份；迟到回执或撤权竞态仅在实际触发时记录，不把普通切号视为精确竞态覆盖。同身份房间失权仍可展示原未知事实，但不能获得发布权限。原窗口关闭后如需再启动，使用新的完整隔离运行，不能复用已结束 launcher 下的可执行文件。

### 成员提案与房主审阅增量

已完成前述账号隔离检查后，可在新的隔离运行中只补本节，无需重测全部 Desktop 页面。

- 成员编辑一个设置，预览后取消，确认房间未变；重新预览并提交。提案草稿与普通 Arena 草稿分离，成员提交摘要不替代完整房间配置。预览后再编辑或同步配置，旧确认应失效，须重新预览。同步若会丢弃修改，应先询问，取消应保留内容。
- 使用“随机匹配”获取合成公开角色，再预览其引用。mock 只提供固定随机角色及其新鲜单卡读取；公开卡列表浏览不在本 harness 范围。`observe` 应看到 `public-card` 的 `random` 和 `read` 摘要。在线卡的版本记录仅用于观测，不能要求精确版本一致；内置预设引用仍按实际目录与 digest 校验。来源不可用应明确提示，不能自动反复随机或改用本地缓存。
- 成员可撤回自己的待处理提案；房主可拒绝、普通接受或选择部分项接受。普通接受后观察两端权威配置更新；房主原本机草稿不得被替换或自动再次发布。需要冲突时，在成员提案待处理期间由房主按上一节改变同一设置，再审阅冲突并明确选择覆盖；审阅基准变化后旧覆盖选择应失效。无关设置的修订前进不能单独阻止普通接受。
- 分别在下一次对应操作前装备 `fault proposalSubmit`、`fault proposalWithdraw`、`fault proposalResolve`，再明确提交、撤回或审阅。服务完成真实业务后丢响应；不得自动重发。若出现未知，使用页面对账入口读取：待处理、缺失或关联不足应继续保留防重发围栏；可信关联终态可结束等待，但仅确认当前业务目标，不证明原 HTTP 成功。WSS 可能先交付可信终态，此时不强求页面必须停在未知。
- 未知时明确“结束本机跟踪（不取消服务器操作）”，确认后先“重新连接并对账”，再重新预览或选择操作。原未提交草稿应保留，旧预览与迟到来源结果不得复活。禁止把结束跟踪当作取消服务器操作或自动重新提交。
- `fault proposal-unsupported` 在下一次合法提案写进入业务前拒绝。分别对提交、撤回、审阅装备并触发，确认明确不支持提示、对应 `room-http` 为 400 且没有丢响应、提案与配置不变，也没有 legacy 回退。无效 owner header 不消耗故障。该故障只模拟前置拒绝语义，不代表运行旧版本完整服务。
- 带未提交修改离开或断开时，取消确认应保留稿件；明确结束后恢复原普通 Arena 草稿、结果及模型选择。切账号或 Document 退役后旧提案确认和来源回调不得写入新身份。精确断连、迟到回执竞态只在实际触发时记录；下方战报场景不替代提案的精确竞态验收。

### 当前房间战报读取增量

沿用上方完整命令链，在新的隔离运行中创建一个房间并让 101、202 都加入。这里使用服务端固定正文；没有真实账号、模型调用或生成写入口。fixture 只绑定该房间和 epoch；不能传任意房间 ID、正文、URL 或文件路径，也不能覆盖正在运行的 fixture。

1. 控制台输入 `observe` 保存起点，然后输入 `generation seed`。两端应自动读取同一当前战报并显示实时预览；仅有 running 状态不能显示“战报已完成”。`generation.readRequests`、`readDispatches` 应增长，房间配置、本机普通草稿和模型偏好保持原样。
2. 输入 `generation delta`，确认预览追加一次。再输入 `generation gap`，该场景仅在 fixture 的每条 WSS 连接中丢掉固定一条正文帧，再交付后续帧；真实 actor 的序列仍连续。两端应以 GET 重取基线、补齐缺口，没有重复正文，也不能把预览宣布为最终权威结果。`deltaFrames` 统计 actor 成功发布帧数（delta 加一、gap 加二），`droppedFrames` 统计实际逐连接丢帧数（双窗通常加二），不要将两者解释成同一种计数。
3. 输入 `generation disconnect`，只断 fixture 房间的 WSS，`disconnections` 按实际断开的连接数累加。观察两端失去在线证明，然后用新 ticket 重新连接，收到新 snapshot/presence 后恢复预览；HTTP mock 不停机。记录是否自动恢复，以及 ticket/session/generationRead 的实际轨迹。若只能点击“读取房间并重连”恢复，单独记为显式恢复，不能宣布自动重连通过。与起点对照，不能重发创建、加入或其他业务写请求。
4. 输入 `generation complete`。terminal 控制事件只表明生成状态；须等新的 generationRead 成功、完整正文验证结束，才显示“战报已完成”和“最终内容已从生成记录恢复并核验”。确认两端最终正文一致；此步骤仍是合成终态读取，不是模型或 durable 生产存储验收。
5. 本轮最后输入 `observe`。`startDispatches`、`cancelDispatches`、`modelDispatches` 必须全部为 0；正常人工读取流程的 `startRequests`、`cancelRequests`、`modelRequests` 也应为 0。请求尝试与实际分派分别计数，拒绝路由的负例会增加尝试计数，但不得增加分派计数；计数独立于有界 trace，不因 `seed`、`complete` 或 trace 淘汰而归零。`modelRequests` 仅统计两个 mock listener 收到的 Native 既有四条固定 POST 模型路径请求，不代表整个操作系统的网络活动；mock 不构造模型 port，`modelDispatches` 保持为 0。

大正文用另一套新的副本、状态目录和完整命令链。两人加入唯一房间后，用 `generation seed-large` 替代 `generation seed`。初始正文固定为 1,048,576 UTF-8 字节，末尾是“验收尾标：月光🌙终章”；先用“导出当前完整正文”核对字节数、多字节字符和尾标，再完成上述 delta/gap/disconnect/complete 流程。它跨过普通房间响应与分片门槛；长预览可以折叠，不能把折叠误判为传输丢失。这不是 73 MiB 上限、内存峰值或真实模型长报告的验收。

迟到读取需要单独的运行，分别验证 owner 退役和换房：

- 完成 `generation seed` 且两端基线读取结束后，只让 202 点击“断开本机房间连接”。控制台输入 `generation hold-read`，再由 202 重新打开大厅并加入原房间；101 保持不操作。看到 `observe` 的 `readHeld: true` 后，才说明已截住一条原身份的 GET；单独装备 hold 不算触发成功。
- owner 场景：202 在读取被截住时重新登录同一合成账号，或切换到另一合成账号。待旧 owner 退役后输入 `generation release-read`；旧正文、完成标记和错误不得写入新 owner 页面。
- 换房场景：另一套新的运行先完成 `generation seed`，再由 101 断开本机连接并创建另一个房间，提前备好新房间入口。随后按同法截住 202 对原房间的读取；202 断开旧连接并加入已准备的新房间，再输入 `generation release-read`。旧房间响应不得在新房间显示。fixture 和被截住的响应始终属于原房间，控制命令不会把它们重新绑定到新房间。
- Native HTTP 期限为 15 秒，mock 的单个 hold 槽最多保留 30 秒。精确迟到实验须在 `readHeld: true` 后、原 HTTP 期限内完成身份/房间变化并释放；可另测更快的 Document 重载或断开，但不能用它替代未触发的 owner/换房竞态。若读取已超时、先行取消或窗口已关闭，记录实际边界，不能当成成功交付的迟到响应竞态。每项保存触发顺序、`observe` 和页面结果。Node loopback 自检能证明 mock 的 HTTP/WSS 场景，不证明 Windows 的 Native、WebView2 或页面围栏已经通过。

控制台只接受 `fault create|join|leave|close|config|config-unsupported|proposalSubmit|proposalWithdraw|proposalResolve|proposal-unsupported`、`generation seed|seed-large|delta|gap|disconnect|complete|hold-read|release-read`、`observe` 和 `stop`。一次只装备一个故障；两个 `unsupported` 模式在下一次对应合法协议请求进入业务前拒绝；其余 fault 模式在下一次对应成功业务完成后丢响应。generation 是封闭的本机合成场景，不是任意控制协议。`observe` 输出有界操作/状态摘要及独立单调计数，不含 cookie、ticket、PKCE 或正文。关闭两个 App 自然结束；`stop`/Ctrl+C 只终止本次拥有的子进程。非预期 App 或 mock 退出按失败保留，不能当作验收通过。

```powershell
node scripts/desktop-room-acceptance.mjs verify --state-root $State
```

状态目录保留最小隔离 manifest、两份临时 patch/config、构建可执行文件指纹、退出状态和有界 mock 观察。补充人工步骤结果及必要截图。`verify` 只核源码/副本/构建一致性，不自动宣布 Windows 验收通过。失败后保留目录，使用新的副本和命名空间重跑；脚本不自动删除 keyring、AppData 或用户资料。

## 房主停止当前生成：独立合成模式

此模式有明确合成 cancel 派发，与上文只读模式分开。使用新副本/状态目录，按同样步骤完成 preflight、prepare 和 build；启动改用：

```powershell
node scripts/desktop-room-acceptance.mjs self-check-cancel --state-root $State
node scripts/desktop-room-acceptance.mjs launch-cancel --state-root $State
```

两个合成账号创建/加入同一房间后：

1. 输入 `generation seed-large`，等两端读到预览；输入 `generation cancel-wait`。房主点“停止当前生成”后确认，成员不能发起停止。应保留在线证明与实时连接；HTTP 成功但仍 running 时显示等待终态，不可双击重发。`observe` 中本轮 `cancelDispatches` 只增加一次，`startDispatches/modelDispatches` 始终为零。
2. 输入 `generation cancel-complete`，原目标经 WSS/GET 核对后显示取消终态，不能显示已完成报告。再点只读核对或刷新不会补发 POST；保留完整观察与截图。
3. 新一轮 `generation seed` 后输入 `fault generationCancel`，再明确确认停止。mock 在合成业务成功后丢回执；应用应保留或通过同目标终态解除未知，只使用 GET/WSS 核对，不再 POST。观察 `cancelDispatches` 仍只增加一次。
4. 单独检查取消确认打开后切账号、房间或目标时旧确认失效；终态先到、旧 HTTP 后到不得恢复可停止状态。若原目标无法核对，必须显示未知并继续防重发，不能以新生成状态代替原目标结果。

此模式只允许新增固定取消路由、`fault generationCancel` 与 `generation cancel-wait|cancel-complete`；原 `launch`、`self-check` 继续拒绝这些能力并强制零 cancel 派发。`stop` 仍只关闭本机测试进程。self-check 证明合成 API/WSS 场景，不代替真实 Windows 页面和 Native 路径验收。

## 边界与维护

- 正式 Rust 源、端点、ACL、CSP 和构建配置没有测试 override；临时补丁仅写两个 disposable checkout，按唯一锚点和原 HEAD 重算，源码漂移即拒绝
- PKI JSON 中的 CA、证书和叶私钥全部是公开合成测试材料。额外根仅在两份副本进程中加载；不能安装到系统信任、修改 hosts、关闭证书验证或绕过浏览器安全警告。证书过期时更新测试 fixture，再重跑无根/错主机名拒绝用例
- Room 保持真实平台 TLS verifier、hostname/SNI/chain 校验；Node 自检证明自身 HTTPS/WSS 服务与负例，不替代 Windows 平台验证器实测
- mock 复用正式 Hono、membership/actor、ticket、防重放及 presence；账号和存储端口为有界合成内存。它不验证 Redis/D1、生产部署或真实账号。额外提供固定合成公开角色的随机与单卡读取，以及通过当前成员校验的单条 current-generation GET；历史列表/历史视图、生成启动与其余未知/云路由直接拒绝；取消只在上述显式合成模式开放，不代理到公网。fixture 使用内部 actor 能力建立和推进合成状态，不接 generation service.start 或模型端口
