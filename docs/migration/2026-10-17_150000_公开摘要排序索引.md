# 公开摘要排序索引

## 适用范围

`drizzle/0021_public_data_card_summary_indexes.sql` 只增加四个 partial 索引（两个排序 × 全类型/单类型前缀）：公开、审核通过且未软删除的摘要列表，分别对应 `created_at` 和 `likes` 排序。排序表达式与 `data-card-summaries.ts` 一致，保留 NULL 回退、更新时间和 ID 的并列顺序。单类型入口使用 `type` 等值前缀，避免有统计信息后退选旧索引并排序；全类型索引尾部的 `type/user_id` 仅帮助过滤与用户存在性连接。多类型、搜索、标签和深 offset 仍可能扫描很多索引项。

公开摘要已经先分页再计算 JSON 与标签；索引消除的是内层选页排序，外层保留当前页的 ORDER BY（SQLite 也可能消除该实际排序）。多类型 IN 与 `includeLegacyQuestionnaires` 的 OR/JSON 条件在有统计信息时仍可能选旧索引并排序，不保证覆盖。准确总数仍遍历匹配集合。`updated_at/usage/favorites`、旧全文列表原始列排序及 `public_since` 不在本次覆盖范围，不能把单页行查询改善当作接口整体延迟保证。旧全文列表只补 `id DESC` 并列排序，不改变原 NULL 策略。

## 发布与回退

- 使用现有安全迁移流程核对目标环境与待执行迁移，再由维护者安排应用；源码存在不表示远端已迁移。应用代码不强制指定索引，缺索引时保留原查询语义
- 建索引会扫描原表，并为符合 partial 条件的每行写入四个索引项，需要临时空间、数据库存储和写入预算，安排低峰并先在测试库核验；它不搬移或清理卡片正文
- 后续点赞维护两条赞数索引，创建/更新时间变化维护相关排序键，公开/审核/软删除状态变化可能同时增删四个索引项。私有、未通过审核及已删除内容不占这些索引项
- 核对 `sqlite_schema` 中的实际定义；`IF NOT EXISTS` 不会修正已有同名错误定义。按 [D1 索引指引](https://developers.cloudflare.com/d1/best-practices/use-indexes/) 在建索引后安排 `PRAGMA optimize`，再用实际绑定参数 SQL 检查计划与既有查询元信息，不增加请求监控采集
- 性能回退只移除 `idx_data_cards_public_summary_created`、`idx_data_cards_public_summary_likes`、`idx_data_cards_public_summary_type_created`、`idx_data_cards_public_summary_type_likes`，保留旧索引与数据。用后续迁移记录 DROP；不改写已应用迁移历史，回退应用代码也不要求删索引

## 验证方法

`apps/web/tests/public-data-card-query-plan.test.ts` 捕获真实 Drizzle SQL 和参数，在无统计及 ANALYZE 两态检查迁移前后结果等价、NULL、同值分页、筛选、作者存在性、撤回/审核/删除以及幂等与回退。SQLite 计划输出不是稳定 API，测试只检查相关索引和排序性质，不绑定节点编号。

可选设置 `PUBLIC_CARD_QUERY_BENCHMARK_DIR` 后运行该测试，导出纯合成数据库、真实查询及迁移供本地测量。计数与取页分别比较，记录索引前后计划、排序次数、VM 步数和耗时；VM 步数不等于 D1 `rows_read`。本地 SQLite 不能代替远端 D1 的计划与生产延迟验收，尤其不能把测试夹具的数据分布视为线上分布。

表达式索引依赖[表达式匹配](https://www.sqlite.org/expridx.html)，partial 索引依赖[查询蕴含可见性条件](https://www.sqlite.org/partialindex.html)；以后修改排序或权限条件时同时运行这组测试。

本次不改缓存。公开接口已有短期 URL 缓存；增加缓存期限或合并缓存键之前，必须另行验证身份无关响应、审核/撤回失效以及 `refresh` 唯一 URL + `no-store` 的 fresh-read 屏障。
