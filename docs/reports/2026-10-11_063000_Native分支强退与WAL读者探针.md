状态：DESK-105 内部资源计量切片，真实四 case、冻结 Native 与 clippy 通过；本轮完整 workspace CI 通过。仅 opt-in 测试、串行 runner 和文档；生产逻辑、IPC、ACL、Hosted v1、两页能力、预算与 checkpoint 策略未变。

## 范围与边界

依据 [DESK-105 窄合同](../specs/2026-10-10_233200_连续故事分支窄合同.md)，承接[未知结果围栏](./2026-10-11_041200_Native分支未知结果围栏验收.md)、[长记录资源计量](./2026-10-11_045500_Native分支长记录形状资源探针.md)与[借用解析](./2026-10-11_054500_Native分支借用解析与键比较.md)。四个固定 case 均使用独立私有目录和真实 SQLite9 小库；源通过四次合法 start/continue 保存建立，每章序列化原件精确 2 MiB，章合计 8 MiB，另有原 session、seed、checkpoint 和索引等开销。大内容是 opaque 扩展，不扩大正文或新增包限制。

三个强退 case 分别在首次 `copy-chapter` 后、`before-commit`、`after-commit` 的既有 hook 暂停。writer 先 sync 保存原 manifest、requestDigest、instance、完整预期 receipt、三件新增包和源全列指纹，再输出 flush 后的 nonce/PID/step 标记。runner 只对自己创建且标记匹配的 Popen 子进程执行 SIGKILL；不搜索或操作其他进程。真实 signal 退出与 stdout 标记分别保存。

重开为全新进程：前两 case 要求目标三表均零、exact receipt 不存在；after-commit 要求完整目标 1 session / 5 chapters / 6 checkpoints，exact receipt 与强退前冻结预期相同。重复查三次且 SQLite total_changes 不增加。新 instance 必须不同；无 receipt 的原冻结包走实际 begin/append/end，要求 Stale、零写 hook、零 SQLite changes，再显式 abort 释放临时上传。原 generation 的缺 receipt 不授予 owner 自动重保存权限。

每个重开均验证源全部持久列的类型/长度标签指纹、原记录 hash、integrity_check、foreign_key_check、branch 全库关系审计和启动临时文件回收。after-commit 另外逐条对拍复制章/CP 的原 raw token 与允许身份变化。

## 有界 WAL 长读者

唯一 LocalLibrary writer 已开库后，runner 启动独立只读 sqlite 进程，BEGIN 并实际 SELECT 建立旧快照；握手后才写。固定最多三个独立 target，每次从同一个四章源的 k=1 分支，复制一章约 2 MiB 及对应边界，未对三个 target 重复复制完整四章。每次 commit 后记录 PASSIVE checkpoint 的 busy/log/checkpointed；至少一次 log > checkpointed 才算有效。旧 reader 必须仍看不到任何新 target。

reader rollback/close 并退出后，原 writer 执行 TRUNCATE checkpoint，要求 `(0,0,0)` 且 WAL 长度为零。最后新进程重开，验证三个完整目标、各冻结 exact receipt、源指纹和完整性/外键/branch 审计。没有用第二个 LocalLibrary 争独占锁或触发启动 cleanup，也未改自动 checkpoint 策略。

## 测试保护与测量口径

runner 开始每个 case 前要求可用空间至少 512 MiB；运行中低于 384 MiB、私有 fixture 文件长度合计达到 128 MiB，或四 case 共享的 stdout/事件/采样日志累计超过 16 MiB 即终止自有子进程并保留失败证据。构建另有 256 MiB 空间保护。以上仅本机测试保护，不是产品 cap，也不是 OS ENOSPC 验证。

采样约 25 ms；RSS/目录和单文件长度是非原子观测，不是瞬时绝对峰值或实际分配块峰值。每 case 一次 Linux debug 样本，不代表统计稳定性、任意历史容量或其他平台表现。不把进程耗时或 end 总耗时称为精确写锁持有时间。

### Runner 自身的失败安全验证

独审发现草稿按错误时序要求冻结 manifest、并在进程登记前写日志以及 signal 前日志 IO 失败可能漏清理 child，均在真实资源运行前修复。现在 source 指纹在 fixture 后保存，原 manifest/parts/receipt/digest/instance 在 crash-ready 后、SIGKILL 前保存，WAL 六个目标 artifact 在 commits-ready 时保存。先登记所有 Popen，再做可失败日志，日志 ENOSPC 不阻止自有句柄 SIGKILL，清理继续遍历其余进程且有界等退出。

独立小型合成协议四 case 通过；bad PID、bad nonce、128MiB sparse fixture、16MiB累计日志和超时负例全部 fail closed、所属子进程回收、失败 fixture 保留。注入 spawn-event OSError 和所有 signal-log OSError 的回归中，三个自有子进程均 -9；另验证低于384MiB保护。合成结果仅验证 runner，不代替上述真实 Native 数据库证据。
