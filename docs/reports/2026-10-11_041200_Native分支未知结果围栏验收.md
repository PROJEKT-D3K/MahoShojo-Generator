## 原缺口与当前机制

原 `Stage.branch_unknown` 会随 abort、15 分钟 expiry 或新建上传消失，提前创建的同 operation 第二 token 也没有共享这项状态。即使单 token 测试通过，原 generation 仍可能重新取得写入机会。

现由同一 staging mutex 保护上传与轻量 `operation → 原 target/requestDigest` 围栏：

1. 实际 COMMIT 结果未知或显式 ROLLBACK 失败时，先在锁内撤销同 operation 全部预建上传（含不同 target/digest、线性 carrier），再以一个轻量围栏替代；返回前已释放全部相关临时文件和字节预留
2. 原精确请求的旧 token 只保留原 receipt 查询，至多来自现有两个槽；不保留全文、manifest 或文件。不同 target/digest 的旧 token 返回 stale，不能冒领原请求 success
3. abort / expiry 只回收上传，不删除围栏；公共 begin_stage 对已围栏 operation 的线性伪装也拒绝。无关正常线性保存保持原语义
4. 独立 branch_receipt 不依赖上传；absence、mismatch、查询 IO 均不释放写入围栏。exact success 仍优先于源存在、当前 instance、source CAS 和目标后续 revision
5. `pending_save` 在实际保存边界共用operation围栏，按既有 admission→stages→connection 顺序持锁覆盖写事务，关闭 branch 已释放connection但尚未安装围栏的竞入间隙；unknown前已sealed/prepared者也拒写。pending全文与durable attempt保持，读/导出可用，无关operation仍能正常保存
6. 即使查到 success 也保留轻量围栏，否则删除目标/receipt 后可重写原 generation。明确 ROLLBACK 成功不建围栏，原冻结包可显式重试并重新核 CAS

## 有界资源与可用性代价

上传与未知围栏共同占原 `MAX_STAGES=2`，未发布 pending upload 也使用同一 admission 计数。围栏替换上传不双算槽；上传字节回收后，剩余一个槽可预留完整原 128MiB 总预算。未知身份不因容量逐出，原 384MiB 逻辑边界不变，没有新增历史累计上限。

同一实例出现两个未知 operation 后，新的 Direct / branch / pending 上传会 Busy，直到实例结束；已有 pending upload 幂等 begin 不重复占槽。这个保守可用性代价是有界且不驱逐未知身份的结果，不能隐藏为“正常容量完全不变”。查询和删除不释放身份槽，全文/文件空间已释放。

围栏不落盘，不是永久 ledger。重启或 restore 建立新 instance 并释放内存槽，新任务可继续；原冻结 manifest 的 source descriptor.instance 已过时，无 exact receipt 则拒写，有 exact success 则仍能确认。后续 owner 必须保持原 generation 的 operation、target、descriptor 和 digest 冻结，不为旧 generation 重新构造请求。
